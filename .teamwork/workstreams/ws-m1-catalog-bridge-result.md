## Learnings
- Catalog bridging via getter alias (`Object.defineProperty` with get/set) keeps `parameters` backward compat for tests asserting parameters while exposing `inputSchema` for spec adapter; setter syncs ensures both stay consistent even if someone mutates inputSchema. This avoids duplicating JSON Schema definitions and keeps src/tools diff minimal (only index.ts central shim, not 7 module files). Alternative of editing each tool file to duplicate inputSchema would risk divergence and lint churn.
- Keeping `registerAllWebMCPTools` sync void preserves backward compat for existing tests (WebMCPEngine.test.ts forEach without await) and for M2 bootstrap fallback; adding `registerAllWebMCPToolsAsync` with Promise.allSettled provides Q10 semantics without breaking sync callers. Engine's internal Promise bridging handles actual document.modelContext.registerTool Promise; wrapping sync register in Promise.resolve gives allSettled semantics cheaply.
- Snake_case Q5 validation via regex ^[a-zA-Z0-9_.-]{1,128}$ allows dot and dash but all 40 use snake_case underscores, so grep gate PASS. Keeping names unchanged is critical for hackathon reviewers testing `await document.modelContext.getTools()` expecting exact 40 snake_case names.
- Approval gates Q6 must stay application-level (pendingApprovalId staging) not native elicitation outputSchema; current catalog has 0 true-gated tools, but engine wrapper correctly handles dummy true case, so future true-gated tools (e.g., safety proposals) will still stage correctly. Not switching to native keeps demo reproducible without browser elicitation.
- Vault patientId bridging must be via localStorage `carecanvas_active_user` at call time, not cached at register; our catalog execute handlers correctly use context.patientId which engine derives at call time, so FileReader drop path (DocumentDropzone) staging creates fact for correct patientId. Node probe without jsdom fails localStorage check, but jsdom probe passes — highlights importance of testing with jsdom for vault paths.
- Engine core and catalog bridge are parallel safe only because ownership is disjoint; we verified via detectConflicts and avoided touching src/core/webmcp files. This allowed both M1 workers to pass without merge conflicts.
