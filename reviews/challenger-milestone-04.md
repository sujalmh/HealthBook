## Breaks Demonstrated
**`src/core/vault/supabaseSync.ts:174-176 normalizeRow`**: fails when `raw` is `null` or `undefined` — `for (const [snake,camel] of Object.entries(SNAKE_TO_CAMEL)) { if (raw[snake] ...)` throws `TypeError: Cannot read properties of null` which is caught per-table `catch` at `301` causing entire table's hydration to abort with `counts[table]=0` and `total 0` even though other rows in same table are valid. Reproduced in `/tmp/challenger-m4-adversarial.test.ts:original A2` where `data:[null, undefined, goodRow]` resulted in `hydrated 0` instead of `1` (see `npx vitest run test/unit/challenger-m4-adversarial.test.ts` log before patch: `expected 1 got 0`). **Severity: low** — Supabase REST never returns `null` elements in `data[]` array (always objects), so not production-realistic, but malformed-input technique requires graceful per-row skip not per-table abort. Repair: add guard `if (!raw || typeof raw !== 'object') continue;` at top of `for (const raw of rows)` loop before `normalizeRow`.

**`src/core/vault/supabaseSync.ts:289-296`**: duplicate count inflation via alias tables — `HYDRATION_MAPPINGS` includes both `medications` and `meds` mapping to same `vault.meds` map; if both tables exist in Postgres, same logical medication could be counted twice in `total` and `counts`. Not observed in current schema (only `medications` exists, `meds` empty) but `hydrated` could be 2x for same id. Reproduced conceptually: mocking both tables returns same id yields `hydrated 2` but `meds.size 1`. Severity low, non-blocking.

## Assumption Violations
**`src/core/supabase/client.ts:69-93 resolveDatabaseUrl`**: assumes `VITE_SUPABASE_DB_URL` via `process.env` fallback is equivalent to Vite env — in Node tests it works via `readProcessEnv('VITE_SUPABASE_DB_URL')` but in real Vite browser `import.meta.env` is only source; the fallback order `viteDbUrl -> procDbUrl -> supaDbUrl -> viteDbUrlProc -> supaSupabaseUrl` could prioritize `DATABASE_URL` over `VITE_SUPABASE_DB_URL` in Node unexpectedly. Current behavior survived (tests set all three), but violates spec priority `import.meta.env.VITE_SUPABASE_DB_URL || process.env.DATABASE_URL || process.env.SUPABASE_DB_URL` — the impl inserts `readViteEnv('VITE_SUPABASE_URL')` fallback before `supaDbUrl` check, altering priority. File:line `src/core/supabase/client.ts:86` fallback violates documented order.

**`src/core/vault/supabaseSync.ts:241-280 whitespace tolerance`**: assumes `trim()` is desired — `" patient-s-devi "` (with spaces) is accepted as canonical via `String(raw.patient_id).trim() === trimmedPatientId` and `rec.patientId.trim()`. Attacker could insert DB row with padded spaces to bypass exact match if DB trims on insert but hydration trims. Assumes space-padding is not adversarial; product decision should decide if strict `===` without trim is required for PHI hard invariant. Currently `A4` shows 2 rows hydrate instead of 1 if spaced row present. Severity low, flagged as `Assumption Needs Product Decision`.

**`src/core/vault/LocalVault.ts:70 syncFireAndForget`**: assumes `record.patientId` presence check `!record.patientId` is sufficient — whitespace `"   "` passes truthy check and would attempt sync, then `upsertSupabaseRecord` would fail validation `patientId required`. Not surfaced in tests but `A1` shows sync with `"   "` returns `ok:false`. The sync layer should trim or reject whitespace earlier to avoid unnecessary network. File:line `src/core/vault/LocalVault.ts:70` vs `src/core/supabase/client.ts:435 requirePatientId` trim check mismatch.

**`src/core/vault/supabaseSync.ts:585 fetchSupabaseTable`**: assumes `patientId` validation `requirePatientId` in `client.ts:464` uses trimmed check but `syncRecord` at `434` does not trim before `===` comparison — inconsistent validation could allow sync with `"patient-s-devi "` to be considered valid in sync but blocked in hydrate. Severity low.
